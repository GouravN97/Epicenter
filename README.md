## The problem

Distributed systems produce a constant stream of metrics. When something breaks, dashboards light up
everywhere at once: a slow database makes every service that calls it slow too, and the on-call engineer is
left staring at a wall of red charts trying to work out which one is the cause and which are symptoms.

A useful monitoring platform has to do three things under load:

- **ingest** thousands of events a second from many sources, rejecting malformed, duplicate and excessive
  traffic without falling over;
- **deliver** live updates to many browsers at once, each seeing only what it is allowed to see, without
  re-sending the whole state every second;
- **combine history with live data** so a chart that loads ten minutes of history and then keeps streaming
  never shows a gap or a doubled point, even across reconnects.

## What Epicenter does

Epicenter monitors a simulated e-commerce company, *ShopStream*: 48 servers across 3 regions running 9 services
that call each other. Load enters at the edge gateway and flows down a real dependency graph, so when one
service degrades, latency and errors propagate up to everything that depends on it, as they would in
production.

On top of the standard live dashboard, Epicenter adds four things:

| | Feature | What you see |
|---|---|---|
| 1 | **Epicenter tracing** | Alerts that cascade through the dependency graph are grouped into one incident. The map marks the root service, ripples it, and animates the failure spreading outward to its blast radius. |
| 2 | **Chaos Lab** | Admins inject faults (slow a service, kill a node, flood the ingest path with duplicates or malformed data). A scorecard shows how long detection took and whether the right root cause was named. |
| 3 | **Incident replay** | Every incident is a recording. Scrub through it, play it back at 1×, 4× or 16×, then press *Go Live* to rejoin the live stream with no gap or duplicate. |
| 4 | **Pipeline X-ray** | The platform monitors itself: events per second, duplicates dropped, late corrections, write batches, bytes out, event-loop lag and the end-to-end delay every browser reports. |

## Features

**Monitoring**
- Fleet heatmap: one hexagon per node, CPU as fill, status as outline, centre mark and stripes (never colour
  alone). Hover or keyboard for details, click or Enter to open the node.
- Stat tiles with sparklines, a live alert feed (windowed list, acknowledge for SREs and admins), and an
  open-incident banner.
- Node detail: four synced charts (CPU and memory, latency, errors, network), ranges of 5 m, 15 m, 1 h and 6 h,
  history merged with the live stream, and a dashed "same time one hour ago" baseline.
- Topology: live service map with traffic on the edges, p95 latency against each service's SLO, and the
  incident overlay.

**Incidents**
- Incident list and room: epicenter and confidence, timeline with notes, presence of other responders,
  chaos scorecard.
- Replay with a time scrubber, alert markers, play, pause, speed and Go Live. The topology map, the node
  heatmap and the epicenter's chart all follow the scrubber.
- Notifications when an incident opens (once its epicenter has settled) and when it resolves.

**Platform**
- Validated, rate-limited batch ingestion; sliding-window deduplication; 1-second aggregation with late-event
  correction; idempotent bulk writes.
- Team-scoped access control end to end: a payments viewer never receives another team's data, on any socket
  room or REST endpoint.
- Guided tour for newcomers: on first sign-in the app walks through telemetry, alerts, root cause, replay and
  the pipeline, highlighting each part of the screen and checking off hands-on exercises as they are done.
  Restart it from the Tour button. The same material is in [`demo.md`](demo.md).
- Metric filters and JSON export: on a node page, choose which of the eight metrics to chart and export them
  over the selected range; in the alert feed, filter by metric and export the alerts shown.
- Keyboard shortcuts for navigation, time ranges, replay, display mode and the tour; press `?` for the list.
- Works on a phone: the layout collapses to one column with a bottom tab bar.
- Accessible: keyboard operable (including the heatmap), skip link, focus moved to each page's heading,
  screen-reader announcements, status never conveyed by colour alone, reduced-motion support.

## Setup and running

### Prerequisites

- Node.js 20 or newer (`.nvmrc` pins the version)
- MongoDB: a free [MongoDB Atlas](https://www.mongodb.com/atlas) cluster, or a local one, for example
  `docker run -d --rm --name epicenter-mongo -p 127.0.0.1:27017:27017 mongo:7`

### Install and configure

```bash
git clone <this repository> epicenter && cd epicenter
npm install
cp .env.example .env
```

Fill in `.env` (one file in the repository root, read by every part):

| Variable | What it is |
|---|---|
| `MONGODB_URI` | Connection string, for example `mongodb://127.0.0.1:27017/epicenter` |
| `JWT_SECRET` | Any long random string, e.g. `openssl rand -hex 32` |
| `SIM_KEY` | Any long random string; the simulator's agent key |
| `SEED_ADMIN_PASSWORD`, `SEED_SRE_PASSWORD`, `SEED_VIEWER_PASSWORD` | Passwords for the three demo accounts |
| `CLIENT_ORIGIN` | Where the browser app runs; `http://localhost:5173` locally |
| `VITE_API_URL` | Where the browser finds the API; `http://localhost:4000` locally |
| `EMBEDDED_SIM` | `true` to run the simulator inside the server process (used when hosted) |

### Run

```bash
npm run seed        # creates indexes, the demo users, the simulator's agents and the 48 nodes
npm run dev         # API on http://localhost:4000 and the web app on http://localhost:5173
npm run sim         # in a second terminal: 48 simulated nodes reporting twice a second
```

Open <http://localhost:5173> and sign in. The login page has quick-fill buttons for the demo accounts:

| Account | Role | Sees |
|---|---|---|
| `admin@epicenter.dev` | admin | everything, including the Chaos Lab |
| `sre@epicenter.dev` | sre | everything; can acknowledge alerts and add incident notes |
| `payments@epicenter.dev` | viewer | only the payments team's nodes, alerts and incidents |

Simulator options: `npm run sim -- --url http://localhost:4000 --hz 2` (`--dry-run` prints without sending).

### Run the web app without a backend

The client has a complete mock backend, useful for UI work and for trying Epicenter without MongoDB:

```bash
npm run dev:mock -w @epicenter/client     # http://localhost:5173, any password works for the demo accounts
```

The mock runs the same contract (REST shapes, socket events and rooms, access rules) against a deterministic
simulated fleet, schedules a background fault every four minutes, and supports every Chaos Lab scenario.
Add `?mockNodes=500` to the URL to try a larger fleet.

## How data is generated and ingested

**Simulated world** (`simulator/src/world.ts`). 48 nodes across `us-east-1`, `eu-west-1` and `ap-south-1`.
Gateway traffic follows a daily-style wave with noise and propagates down the dependency edges by fixed
call fractions. Each node's CPU follows its share of traffic plus noise; latency is a service's own latency
(rising with CPU) plus the weighted latency of what it calls; errors rise with CPU and with dependency errors.
Because propagation is computed, a fault injected at one service produces a realistic cascade with no
scripting, which is what makes root-cause tracing an honest feature.

**Agents** (`simulator/src/agent.ts`). One logical agent per region collects its nodes' readings and sends a
batch every 500 ms to `POST /api/v1/ingest` with its agent key. Every event carries
`nodeId`, `bootId` (regenerated on restart), a strictly increasing `seq`, a source timestamp and eight
metrics (`cpu, mem, disk, netIn, netOut, lat, err, rps`). On HTTP 429 the agent waits for `Retry-After`;
on network errors it retries with the *same* `seq` values, so retries exercise deduplication.

**Ingest path** (`server/src/http/routes/ingest.ts`, `server/src/pipeline/`), in order:

1. Agent key checked (cached lookup), then a 256 kB body limit.
2. Batch envelope validated with zod; each event validated on its own, so one bad event does not reject the
   batch. Events more than 5 s in the future or 60 s in the past, or for nodes the agent does not own, are
   rejected and counted.
3. Deduplication on `nodeId:bootId:seq` with a sliding window of 1024 sequence numbers per node.
4. Aggregation into 1-second buckets per node. A bucket is finalized 2 s after it ends (time for late events);
   a late event for a finalized bucket updates it, bumps its `rev`, and re-emits it as a correction.
   1-minute rollups are built the same way.
5. The request returns `202` with counts. **No database call happens on this path.**

Finalized points go to the **writer**, which flushes every second (or every 1000 points) with one unordered
`bulkWrite` of upserts on the unique `(nodeId, ts)` index. A correction replaces a pending write, and the
upsert only applies if its `rev` is not older than the stored one, so replays, retries and restarts never
create duplicates. Raw events are never stored; 1-second rollups are (6-hour TTL), plus 1-minute rollups
(7-day TTL).

## How real-time delivery works

All live data flows through Socket.IO. Browsers connect to the `/dash` namespace with their JWT in the
handshake; it is verified once at connect.

**Rooms** let each browser subscribe to exactly what is on its screen:

| Room | Content | Rate |
|---|---|---|
| `fleet:<team>` | changed nodes only: `[tsSec, [nodeIdx, cpu, mem, status], …]` | 1 Hz |
| `topology` | one aggregate row per service | 1 Hz |
| `node:<nodeId>` | each finalized 1-second point, corrections included | on finalize |
| `service:<serviceId>` | service aggregate points | on finalize |
| `alerts:<team>` | alert lifecycle events | on event |
| `incident:<id>` | incident updates, notes, presence | on event |
| `meta` | pipeline statistics and chaos runs | 1 Hz |

- **Small payloads.** Positional arrays instead of objects; node and service ids are sent once (in
  `GET /topology`) and the wire carries integer indexes. A fleet delta lists only nodes whose CPU or memory
  moved by at least one point or whose status changed. A full snapshot is sent once, when a browser joins a
  fleet room, never repeatedly.
- **Selective broadcast.** Nothing is serialized for a room nobody is in. Chart streams skip sockets whose
  send queue is backed up, so a slow browser misses frames (and repairs them from history) instead of making
  the server queue them.
- **Access control.** Every `sub` request is checked: admins and SREs may join anything; a viewer may join
  only rooms of their own teams (and the aggregate `topology` and `meta` rooms). Each socket is limited to
  20 subscription calls per 10 s and 100 rooms.
- **Clock and delay.** A `time` handshake gives each browser its offset from server time. Every browser
  reports its end-to-end delay and frame rate every 5 s (`client:stats`), shown on the Pipeline page.

**In the browser** (`client/src/data/`), telemetry never goes into React state:

- Each chart's data lives in a fixed-capacity, time-sorted typed-array buffer. Its `upsert(t, values, rev)`
  is the client's whole deduplication: history rows, live points, corrections and reconnect gap-fills all go
  through it, in any order, keyed by timestamp.
- One `requestAnimationFrame` loop redraws only charts whose data changed and that are on screen, at most once
  per frame, and pauses while the tab is hidden.
- Subscriptions are reference-counted and batched; panels scrolled off screen unsubscribe after 2 s.
- Opening a chart subscribes first, then loads history, so the two overlap rather than leave a hole. After a
  reconnect it re-fetches from just before the last point it had. Both re-read their newest seconds once
  the server's write buffer has flushed, which closes the last possible gap.

The full design, with diagrams, is in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Testing it

```bash
npm test             # every unit test in the repository (Vitest)
npm run typecheck    # TypeScript across all packages
```

**Things to try** (with `npm run dev` and `npm run sim` running, or in mock mode):

1. **Live and historical together.** Open a node, choose 5 m, then run `epicenter.drop(20000)` in the browser
   console to drop the live connection for 20 s. When it returns the chart heals with no gap and no doubled
   points.
2. **Two browsers, two scopes.** Sign in as admin in one browser and as the payments viewer in another. The
   viewer's socket only joins `fleet:payments` and `alerts:payments`, and requests for other teams' history
   are refused with 403.
3. **Root cause.** In the Chaos Lab, start *Slow database* (any target service). Watch the Topology page:
   the alerts group into one incident, the target ripples as the epicenter and the failure animates up the
   graph. The scorecard records time to detect and whether the epicenter was right.
4. **Replay.** Open the incident, press Replay, switch to 16×, scrub, then Go Live.
5. **Ingest protection.** Start *Duplicate storm*, *Malformed flood* or *10× traffic* and watch the Pipeline
   page: duplicates, rejections and 429s climb while the dashboards stay steady.
6. **Keyboard.** Tab into the fleet heatmap, move with the arrow keys, press Enter to open a node.

**Load testing**: `npm run stress -- --url <api> --nodes 500 --hz 5 --clients 200 --duration 120` drives
synthetic agents and socket clients against a running server and writes [`docs/BENCHMARKS.md`](docs/BENCHMARKS.md).

## Project structure

```
shared/        the contract: topology, zod schemas, wire formats, constants (imported by everything)
server/        Express + Socket.IO + MongoDB: ingest pipeline, writer, history API, rooms, broadcaster
simulator/     load model of the ShopStream fleet and the per-region ingest agents
client/        React app: data layer (src/data), pages, components, and a full mock backend (src/mocks)
tools/stress/  load generator and benchmark report writer
docs/          architecture, benchmarks, implementation plan
```
